# Markdown YAML Skill Registry

**Category:** skill
**Confidence:** production-proven
**Observed in:** [guanyang/open-agent-hub](https://github.com/guanyang/open-agent-hub)
**Compatible with:** python, typescript, any, claude-code

## Problem
AI agent prompts are scattered, duplicated across projects, and impossible to version-control or selectively activate per context—leading to bloated system prompts and inconsistent agent behavior across Claude Code, Cursor, or custom FastAPI agents

## The Logic
1. Define each capability as a standalone Markdown file with YAML frontmatter (id, name, trigger_keywords, category, version). 2. Maintain a machine-readable index (skills_index.json) generated by scanning all capability files. 3. Write a thin CLI or Python loader that reads the index and symlinks or injects only the requested capability files into the target agent config directory. 4. Separate concerns into three layers: Skills (atomic reusable prompt modules), Agents (role-scoped system prompts that compose Skills), Commands (slash-command triggers that invoke Agent workflows). 5. At runtime, agent receives only the Skills relevant to the current task—not the entire library. Pseudocode: load_skill(name) -> read skills_index.json -> resolve path -> read .md file -> inject into system_prompt_context. For FastAPI: store skill files in /skills/, expose GET /skills/{name} endpoint that returns the markdown body, call from agent orchestrator before each LLM invocation.

## Steal This When
- You are building a multi-step agent (Baby agent) and need to inject domain-specific instructions without bloating every prompt with all capabilities
- You want to version-control prompt logic like code and share skills across Draft Terminal and Greenlit without copy-paste
- Your FastAPI agent has more than 3 distinct task types and you need selective context injection per task type
- You want Claude Code or Cursor to behave consistently across all your projects without re-configuring each workspace manually

## Gotchas
- Index file (skills_index.json) can go stale if skills are added manually without re-running the scan—add a pre-commit hook or startup check
- Symlink-based activation breaks in Docker containers and serverless environments—copy files instead of linking for deployed agents
- YAML frontmatter parsing adds a dependency (use python-frontmatter or gray-matter)—validate schema on load or silently wrong metadata causes wrong skill selection
- Skills composed inside Agent system prompts can exceed context windows if too many are activated globally—enforce a max-skills-per-agent limit
- Trigger keyword matching is naive string matching in the reference impl—for production use embedding similarity against skill descriptions instead
